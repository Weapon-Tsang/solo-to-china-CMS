# 内容生产策略 1.9 — 流程统一设计（未激活）

状态：设计与实施中。当前生效策略仍为 1.8；交付清单 requirementsVersion=1.3。
本稿不是上线声明，不触发历史素材重新分析、重新批准、模型调用或发布。

## 1. 目标与根因

目标不是把每个来源变成文章，而是让人工确认的、有独立编辑价值的读者承诺，
在可追溯证据和可交付资源约束下，经过可恢复、可核算的生产链形成合格草稿。

当前根因不是几个按钮缺失，而是对象、批准语义和状态责任没有统一：

1. 来源分析记录、创作方向和可生产文章都被称为“机会”；来源数量被误认为选题质量。
2. 素材关键词覆盖分被用于解释创作就绪，事实数量加分掩盖具体承诺的证据缺口。
3. 推荐、单一路径、人工命题各有入口，却没有统一展示批准了什么版本和什么边界。
4. 内容质量、媒体缺失、页面未完成、模型请求失败混入一个失败状态和扣分，恢复器难以选择正确责任阶段。
5. UI存储状态、当前任务状态、旧修订审核结果并列而缺少版本说明，导致“排队即改写”的误读。

代码证据：原 `frontend/src/components/dashboard.jsx` 把 pendingRecommendations 与
contentPipelineItems 相加后显示为“选题发现 / 个候选主题”。这是不同对象混算，
不能据此推断独立选题数或解释正文质量。首批实现已取消相加，分别展示来源建议与内容流程记录。

## 2. 核心对象与唯一职责

| 对象 | 负责什么 | 不代表什么 |
| --- | --- | --- |
| 来源/证据 | 保存原文、素材、授权、观察时间、出处和历史 | 不承诺每条来源都会写文章 |
| 来源分析建议 | 解释这份来源可以如何利用 | 不是新的已批准选题 |
| 创作提案 | 具体目的地、目标读者、问题、承诺、范围、创作方式、所需证据与资源 | 不因潜力分高自动生产 |
| 批准记录 | 人工确认具体提案版本及生产边界 | 不等于批准同来源所有方向，更不等于批准公开发布 |
| 生产任务 | 为已批准提案生成并校验指定版本产物 | 不重新发现需求或擅自扩写范围 |
| 交付包 | 通过正文、事实、媒体、页面一致性校验的草稿 | 不承诺排名、索引、引用或自动公开发布 |

保留单来源授权改编、窄题专题、多来源综合三种方式；不存在强制每篇多来源的统一门槛。
相似提案按目的地、读者承诺、内容类型和范围分组供编辑比较；只是分组，不自动合并/删除。
同一城市但不同天数、地点和体验可以并存；同一题目的新增来源优先作为补充证据展示。
不新增读者需求发现、GSC选题、外部问答挖掘或AI需求探索模块。

## 3. 统一主流程与分阶段准入

人工选材 → 来源分析/知识积累 → 创作提案 → 人工确认 → 规划与选证据 →
正文生产 → 正文事实审核 → 媒体/页面编排 → 最终一致性审核 → WordPress草稿交付。

人工命题直接进入同一个“创作提案”对象，不另建一套生产标准。
先利用现有Brief、Draft、AST、QA与契约兼容层实现，不一次改写全部数据库。

### 提案确认前

- 展示明确的读者承诺和不覆盖的范围，不用概括性城市标签代替。
- 展示素材匹配及缺口、可能重复的已有/待产提案、所选生产方式。
- 素材覆盖分只是说明，不是总质量分；按承诺检查核心事实，而非只数facts/source families。
- 动态或暂定事实允许带日期和适当措辞使用，遵守1.8自动时效共识，不恢复日常人工核验队列。
- 核对需要的媒体获取/渲染能力是否可用；不在此要求尚未生产的最终图片已经上传。

### 批准命令

- 单条默认、指定路径、批量和人工命题必须遵循同一批准约束。
- 命令必须明确提案/路径ID，显示标题、方式和证据范围；默认快捷键也必须显示其具体对象。
- 批量只作用于明确选择的记录；不能以“批准文章”隐式批准全部并行路径。
- 请求重发不重复建候选、不重复入队；陈旧选择与已变化的边界拒绝，返回原因。
- 每项独立原子保存；一项失败不重跑成功项；一次请求、一次UI刷新，模型执行异步进行。
- 批准是可能产生生产费用的确认，不是WordPress公开发布许可。

### 正文与最终交付

- 正文事实审核只评价正文与证据；可先完成独立审核，但不得据此跳过最终页面审核。
- 真实无依据陈述、大纲遗漏、台账不一致属于编辑/证据问题。
- 图片403、组件契约400、地图渲染未实现属于资源/工程问题，不能通过改写正文修复。
- 最终页面以冻结正文/AST为依据，保持值、限定条件、来源关系和必要媒体，不改变组件权属。
- 媒体与页面尚未产生时显示“待完成”，不能伪装成正文质量零分。
- 任何交付前仍需当前正文/证据/媒体/页面版本一致；Research与Commercial隔离不变。

## 4. 菜单职责

- 来源：采集与证据追溯。
- 建议：来源分析与编辑判断；提供批量处置，不再用全部机会数量冒充待批准文章数。
- 创作规划（现“选题”）：人工命题、提案范围确认、素材缺口与待产安排。保留功能，避免重复展示整份来源建议列表。
- 内容：已批准任务的当前阶段、产物、质量结果和唯一恢复入口。
- 异常：按根因与受影响任务分组，跳到同一个内容/证据处理入口，不再另建含糊的“重试一切”。

因此“选题”不是每篇必经的第二次审批，但人工命题和规划职能必须保留。
是否保留独立顶栏入口取决于改版后的使用频率；不能因当前列表重复而删除命题能力或数据。

## 5. 统一状态与恢复原则

各阶段使用同一套状态：尚未开始、等待前置条件、已排队、执行中、成功、失败、待人工决定。
展示实际任务和绑定产物版本；历史失败/旧版本评分单独留在历史，不冒充当前结论。
失败至少包含类别、责任阶段、具体产物/字段、根因、前置动作、允许重试范围及费用提示。
恢复先检查依赖、授权、版本与活动任务，再选择最早失效阶段；不得直接把所有未通过改写成revise_draft。
重新采集只使相关证据/媒体状态改变，不默认重跑所有已批准文章。自动恢复仅限原批准范围与预算允许的任务。

## 6. 分批实施与验收

1. 统一批准语义与单条/批量命令，修正文案和计数。验收：精确路径、不越权、不重复、部分失败重试、只刷新一次。
2. 统一提案/人工命题视图与承诺级素材检查。验收：74个来源不自动等于74个独立可产文章；独立窄题不被粗暴合并。
3. 分离正文事实结果、资源能力、页面一致性与费用状态，接入统一恢复决策。验收：媒体失败不改写正文；旧QA不覆盖新版本状态。
4. 贯通一条正常生产和各类失败恢复的隔离端到端用例，再做浏览器可用性测试。
5. 最后更新生效策略、应用版本、变更记录与部署说明；仅在相关验证完成后发布。

必要反例：无草稿提案、单来源充分窄题、重复承诺、不同范围并行提案、归属错误、缺图、过期签名图、
无依据陈述、正常中文证据到英文表达、400永久输入错误、429临时错误、截断、旧版QA、重复批准、
批量部分失败、正在运行的任务、人工公开发布后的WordPress保护。

## 7. 升级安全

现有原始证据、已批准范围、草稿、历史、人工命题和授权完整保留；迁移先备份并演练恢复。
不把新策略版本追写给旧产物，不在升级时自动重跑付费模型或改写WordPress内容。
已有局部修复需逐一映射到本稿的阶段职责与验收；不符合者调整，不将未完成原型直接打包上线。
